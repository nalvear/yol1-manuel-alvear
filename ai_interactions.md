# Uso de herramientas de IA

Registro de las herramientas de IA utilizadas durante el desarrollo y qué partes apoyaron.

## Herramientas

- **Claude Code (Claude Opus)**: asistente en terminal.

## Interacciones

| # | Fase | Qué se pidió | Resultado / qué se ajustó manualmente |
|---|------|--------------|----------------------------------------|
| 1 | Planificación | Analizar el enunciado y armar una lista de tareas ordenada | Plan por fases con commits intermedios El contrato OpenAPI se escribió antes que el código (commit `docs: contrato OpenAPI`) y el resto de las fases se implementó contra él, para que backend y frontend compartan las mismas reglas. |
| 2 | Setup | Scaffolding del monorepo (workspaces, backend Express + TS, frontend Vite + React + TS) | Estructura base, tsconfig, `.env.example` Node fijado en `.nvmrc` (22). `.gitignore` excluye `.env*` y solo se versiona `.env.example`. `tsconfig.build.json` separado con `rootDir: src` para no compilar los tests en el build. |
| 3 | Diseño API | Contrato OpenAPI de `POST /login` y `GET /score/{rut}` con códigos 400/401/403 y reglas de autorización | `backend/openapi.yaml`, validado con Redocly. Se corrigió un ejemplo YAML mal formado detectado por el linter. Se usa `12.345.678-5` en los ejemplos porque el `12.345.678-9` del enunciado tiene dígito verificador inválido Los códigos de error del contrato coinciden con los de `AppError` (`VALIDATION_ERROR`, `NOT_FOUND`, `INTERNAL_ERROR`). El patrón de RUT de `rut.ts` referencia el de `components.parameters.Rut` del OpenAPI, para mantener una sola fuente de verdad. |
| 4 | Backend base | `AppError` con los códigos del contrato, middleware global de errores y handler 404 | `src/errors/app-error.ts`, `src/middlewares/`. JSON mal formado → 400, errores inesperados → 500 sin filtrar detalles. Tests con Supertest Los errores de `body-parser` se traducen a 400 `VALIDATION_ERROR`. Los 5xx se registran con `console.error`, pero al cliente solo llega un mensaje genérico. Los 401 de token agregan el header `WWW-Authenticate` (cubierto en `errors.test.ts`). |
| 5 | Dominio | Utilidad de RUT (normalizar, validar DV módulo 11, formatear) y score determinista | `src/utils/rut.ts`, `src/services/score.service.ts`. Score = SHA-256 del RUT normalizado mod 101 (rango 0–100 del enunciado). Tests unitarios con casos de DV `K` y `0` Se valida el formato con regex antes del módulo 11. `normalizeRut` elimina ceros a la izquierda y `isSameRut` compara ignorando formato (base de la autorización por RUT). El score usa los 4 primeros bytes del hash: con mod 101 el sesgo es ~2,3e-8, despreciable. |
| 6 | Auth | Usuarios mock y `POST /login` según el contrato | Contraseñas con hash scrypt nativo (sin dependencias), verificación contra un hash ficticio cuando el usuario no existe para no revelar usernames por tiempo de respuesta, JWT HS256 con `rut` solo para `user`. `JWT_EXPIRES_IN` pasó a segundos para cumplir `expiresIn` del contrato `JWT_SECRET` es obligatorio y sin valor por defecto (la app no arranca sin él) y `JWT_EXPIRES_IN` se valida como entero positivo. Comparación de hashes con `timingSafeEqual` y salt aleatorio de 16 bytes por contraseña. Mismo error 401 genérico para usuario inexistente y contraseña incorrecta. |
| 7 | Autorización | Middlewares `authenticate`, `validateRutParam`, `authorizeRut` y `GET /score/:rut` | Cadena en el orden del contrato: 401 → 400 → 403. `jwt.verify` con `algorithms: ['HS256']` fijo (rechaza `alg: none` y otros algoritmos). Los claims se validan además de la firma: `user` sin RUT válido, `admin` con RUT o rol desconocido → `INVALID_TOKEN`. `user` compara su RUT con `isSameRut`, así que cualquier formato del propio RUT es aceptado. Tipado de `req.auth` y `res.locals.rut` por declaration merging. Tests de integración con tokens firmados a mano (vencido, otro secreto, otro algoritmo, `alg: none`). |
