# Uso de herramientas de IA

Registro de las herramientas de IA utilizadas durante el desarrollo y qué partes apoyaron.

## Herramientas

- **Claude Code (Claude Opus)**: asistente en terminal.

## Interacciones

| # | Fase | Qué se pidió | Resultado / qué se ajustó manualmente |
|---|------|--------------|----------------------------------------|
| 1 | Planificación | Analizar el enunciado y armar una lista de tareas ordenada | Plan por fases con commits intermedios. El contrato OpenAPI se escribió antes que el código (commit `docs: contrato OpenAPI`) y el resto de las fases se implementó contra él, para que backend y frontend compartan las mismas reglas. |
| 2 | Setup | Scaffolding del monorepo (workspaces, backend Express + TS, frontend Vite + React + TS) | Estructura base, tsconfig, `.env.example`. Node fijado en `.nvmrc` (22). `.gitignore` excluye `.env*` y solo se versiona `.env.example`. `tsconfig.build.json` separado con `rootDir: src` para no compilar los tests en el build. |
| 3 | Diseño API | Contrato OpenAPI de `POST /login` y `GET /score/{rut}` con códigos 400/401/403 y reglas de autorización | `backend/openapi.yaml`, validado con Redocly. Se corrigió un ejemplo YAML mal formado detectado por el linter. Se usa `12.345.678-5` en los ejemplos porque el `12.345.678-9` del enunciado tiene dígito verificador inválido. Los códigos de error del contrato coinciden con los de `AppError` (`VALIDATION_ERROR`, `NOT_FOUND`, `INTERNAL_ERROR`). El patrón de RUT de `rut.ts` referencia el de `components.parameters.Rut` del OpenAPI, para mantener una sola fuente de verdad. |
| 4 | Backend base | `AppError` con los códigos del contrato, middleware global de errores y handler 404 | `src/errors/app-error.ts`, `src/middlewares/`. JSON mal formado → 400, errores inesperados → 500 sin filtrar detalles. Tests con Supertest. Los errores de `body-parser` se traducen a 400 `VALIDATION_ERROR`. Los 5xx se registran con `console.error`, pero al cliente solo llega un mensaje genérico. Los 401 de token agregan el header `WWW-Authenticate` (cubierto en `errors.test.ts`). |
| 5 | Dominio | Utilidad de RUT (normalizar, validar DV módulo 11, formatear) y score determinista | `src/utils/rut.ts`, `src/services/score.service.ts`. Score = SHA-256 del RUT normalizado mod 101 (rango 0–100 del enunciado). Tests unitarios con casos de DV `K` y `0`. Se valida el formato con regex antes del módulo 11. `normalizeRut` elimina ceros a la izquierda y `isSameRut` compara ignorando formato (base de la autorización por RUT). El score usa los 4 primeros bytes del hash: con mod 101 el sesgo es ~2,3e-8, despreciable. |
| 6 | Auth | Usuarios mock y `POST /login` según el contrato | Contraseñas con hash scrypt nativo (sin dependencias), verificación contra un hash ficticio cuando el usuario no existe para no revelar usernames por tiempo de respuesta, JWT HS256 con `rut` solo para `user`. `JWT_EXPIRES_IN` pasó a segundos para cumplir `expiresIn` del contrato. `JWT_SECRET` es obligatorio en producción (ver fila 11 para el respaldo en desarrollo) y `JWT_EXPIRES_IN` se valida como entero positivo. Comparación de hashes con `timingSafeEqual` y salt aleatorio de 16 bytes por contraseña. Mismo error 401 genérico para usuario inexistente y contraseña incorrecta. |
| 7 | Autorización | Middlewares `authenticate`, `validateRutParam`, `authorizeRut` y `GET /score/:rut` | Cadena en el orden del contrato: 401 → 400 → 403. `jwt.verify` con `algorithms: ['HS256']` fijo (rechaza `alg: none` y otros algoritmos). Los claims se validan además de la firma: `user` sin RUT válido, `admin` con RUT o rol desconocido → `INVALID_TOKEN`. `user` compara su RUT con `isSameRut`, así que cualquier formato del propio RUT es aceptado. Tipado de `req.auth` y `res.locals.rut` por declaration merging. Tests de integración con tokens firmados a mano (vencido, otro secreto, otro algoritmo, `alg: none`). Además de los tests, se probó a mano con `curl` el flujo `POST /login` → `GET /score/:rut`, incluyendo solicitudes que debían fallar (sin token, token inválido, RUT inválido y RUT ajeno) para comprobar los códigos 401, 400 y 403 y el formato del error. Se leyó el código generado de los tres middlewares y, donde no quedaba claro por qué se hacía algo (p. ej. validar los claims además de la firma), se consultó a la IA antes de aceptarlo. |
| 8 | Frontend base | Base del frontend con los estilos corporativos de YOL1: paleta, tipografía y tono de comunicación | Se revisó yol1.com con el navegador y se extrajeron los colores y fuentes de los estilos computados. Design tokens en `styles/tokens.css`; Söhne (comercial) se reemplazó por Archivo expandido, Inter y JetBrains Mono. El coral se oscureció (`#D93D1A`) para el texto de error, para cumplir contraste AA. Cliente API tipado según el contrato, con timeout y un handler que cierra la sesión ante 401 de token. Mensajes centralizados por código de error. Se verificó en el navegador el redirect de las rutas protegidas, el cierre de sesión por token inválido y la vista móvil (se corrigió el layout de login y el botón del header). Se leyó el código del cliente API y del handler de sesión, y se consultó a la IA cuando el flujo de cierre por 401 no era claro. |
| 9 | Frontend vistas | Formulario de login y vista de consulta de score con resultado, con controles de usabilidad para evitar errores del cliente | Validación del RUT en el cliente (formato al escribir y dígito verificador) y chequeo anticipado de permisos para `user` (no se envía la consulta y se ofrece "Usar mi RUT"), sin dejar de manejar el 403 del backend. Prevención de doble envío y de respuestas de consultas anteriores que llegan tarde. Al probar en el navegador aparecieron y se corrigieron tres problemas: (1) el error que aparecía al salir del campo desplazaba el botón y se perdía el clic de envío; (2) se intentaba enfocar un campo todavía deshabilitado, lo que se resolvió con el hook `useFocusWhenIdle`; (3) un error de contraseña sobraba después de un login fallido. Tests unitarios de RUT y de los tramos del score en el frontend con Vitest. Se leyó el código generado de los componentes y del hook `useFocusWhenIdle`, y se consultó a la IA para entender la causa de los problemas de enfoque antes de aplicar la corrección. Se hicieron pruebas de UX de los controles de tipado: en el campo RUT solo se aceptan los caracteres permitidos (dígitos y `K`, filtrados con regex en `utils/rut.ts`) y con largo máximo de 12 (`RutField`), y los campos de login tienen `maxLength` y `autoComplete` apropiados; se probó escribir letras, símbolos y espacios para comprobar que se descartan. |
| 10 | Errores y UX | Pulido de manejo de errores y experiencia | `ErrorBoundary` para que un error de render no deje la pantalla en blanco. Aviso 2 minutos antes de que expire la sesión (no hay refresh token). Título de pestaña por página. Header que pasa a dos líneas en pantallas muy angostas (se detectó un desborde a 300px). Se verificó en el navegador la API caída (mensaje claro, el campo se rehabilita y la sesión se mantiene) y el cierre automático al vencer el token. Se leyó el código del `ErrorBoundary` y del aviso de expiración, y se consultó a la IA cuando su comportamiento no era evidente. |
| 11 | Documentación y cierre | README final y verificación desde un clon limpio | README reescrito: inicio rápido, variables, usuarios de prueba, contrato, errores, decisiones técnicas y mejoras. Para cumplir con `npm install && npm run dev` sin crear `.env`, `JWT_SECRET` tiene un valor de respaldo **solo fuera de producción** (con advertencia en consola). Con `NODE_ENV=production` sigue siendo obligatorio. Esto actualiza lo indicado en la fila 6. Se verificó desde un clon limpio: install, tests, build y dev. También se hizo una prueba de punta a punta sobre la base final (frontend contra backend, flujo completo de login y consulta de score, con casos de éxito y de error) y se repasaron con `curl` los ejemplos del README. |

## Verificación y criterio propio

- **Pruebas manuales con `curl`** de los endpoints (`POST /login`, `GET /score/:rut`), incluyendo las respuestas a solicitudes con error (400, 401 y 403), además de los tests automatizados.
- **Pruebas de UX de los controles de tipado** en los campos del formulario (en especial el RUT, que solo admite los caracteres permitidos por la expresión regular).
- **Prueba de punta a punta** sobre la base final del código (frontend contra backend).
- **Lectura del código generado** antes de commitear cada fase.
- **Consultas a la IA solo cuando algo no estaba claro** en el código implementado, para entender el porqué antes de aceptar el cambio.
